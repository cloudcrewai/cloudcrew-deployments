# Runbook: Customer Managed KMS Key

## Overview
This Customer Managed KMS Key (CMK) is used to encrypt sensitive data, such as data stored in S3 buckets and potentially other AWS services used within the SageMaker ML Platform. It provides granular control over encryption keys.

## Prerequisites
- AWS CLI configured with appropriate permissions
- IAM permissions to manage KMS keys and aliases

## Architecture
A KMS CMK is created within the AWS account. Its policy defines who can use the key and for what operations. In this setup, the key is intended for encrypting data stored in S3 and potentially for CloudWatch Logs encryption as indicated by the IAC excerpt.

## Operations

### Scaling
KMS keys do not scale in the traditional sense. Capacity is managed by AWS. The primary consideration is key rotation and management.
1. Enable key rotation for the CMK to enhance security.
2. Regularly review the key policy to ensure only necessary principals have access.

### Monitoring
Key metrics:
- CloudTrail: Monitor all API calls made to the KMS key to detect unauthorized access or usage.
- KMS key metrics in CloudWatch: Monitor `Decrypt`, `Encrypt`, and `GenerateDataKey` API call counts to understand usage patterns.
- Key state: Monitor if the key is enabled and not scheduled for deletion.

### Backup & Recovery
KMS keys are a regional AWS resource and are highly durable. There is no direct backup/restore process for a KMS key itself. If a key is accidentally deleted, data encrypted with that key becomes irrecoverable. Therefore, careful management and appropriate IAM policies are crucial to prevent accidental deletion.

### Common Issues
### Access denied when using KMS key
**Diagnosis**: Applications or services fail with 'AccessDeniedException' when attempting to encrypt or decrypt data.
**Resolution**: Review the KMS key policy and the IAM policies of the principal attempting to access the key. Ensure both policies explicitly grant the necessary permissions (e.g., `kms:Encrypt`, `kms:Decrypt`, `kms:GenerateDataKey`). Check resource-based policies if applicable.

### Key is disabled or pending deletion
**Diagnosis**: Operations using the KMS key fail because the key is not in an 'Enabled' state.
**Resolution**: Check the key's status in the AWS KMS console. If disabled, re-enable it. If scheduled for deletion, cancel the deletion and ensure it remains available.

## Rollback Procedure
1. Revert the IaC commit that created or modified the KMS key resource.
2. Execute `terraform apply` to remove the key from the configuration. This action should be taken with extreme caution as it may impact data encryption if the key is in use.
3. Verify that no services are actively dependent on the removed KMS key.
