# Runbook: Aurora PostgreSQL Cluster

## Overview
The Aurora PostgreSQL Cluster provides a highly available and durable relational database solution. It is configured across two Availability Zones with one writer and two reader instances for read scalability and fault tolerance. Encryption, automatic backups, and detailed logging are enabled for enhanced security and recoverability.

## Prerequisites
- AWS CLI configured with appropriate permissions for RDS, KMS, and Secrets Manager.
- IAM permissions to access CloudWatch Logs and Alarms.
- Database client tool (e.g., psql) and network connectivity to the database subnets.

## Architecture
The Aurora PostgreSQL cluster resides within the 'App VPC' in private subnets across two Availability Zones (a and b). It utilizes a dedicated RDS DB Subnet Group. Encryption is managed by the 'KMS Key for Aurora' (kms_aurora), and database credentials are secured and rotated via AWS Secrets Manager.

## Operations

### Scaling
1. **Manual Scaling (Instance Count):**
   - Navigate to the RDS console.
   - Select the Aurora PostgreSQL Cluster.
   - Choose 'Add reader' or 'Remove reader' under the 'Database instances' tab.
   - Manually adjust the number of reader instances to meet read traffic demands.
2. **Auto Scaling (for Reader Instances - Requires separate configuration not detailed in blueprint):
   - Aurora supports Auto Scaling for reader instances based on metrics like CPU utilization or connections.
   - Configure an Application Auto Scaling policy targeting the Aurora read replica.
   - Define scaling policies to add or remove reader instances within configured minimum and maximum limits.

### Monitoring
Key CloudWatch metrics to monitor:
- **CPUUtilization:** Indicates processor load on instances. Alarm if sustained > 80% on writer, or > 75% on readers.
- **DatabaseConnections:** Number of active client connections. Alarm if approaching instance or engine limits (e.g., > 90% of max_connections).
- **ReadIOPS/WriteIOPS:** Measures I/O operations. Monitor for performance bottlenecks.
- **FreeableMemory:** Available RAM. Alarm if consistently low (e.g., < 15% of total memory).
- **AuroraReplicaLag:** For reader instances, tracks replication lag. Alarm if > 300 seconds.

### Backup & Recovery
- **Backup Schedule:** Automated daily snapshots are taken. Backups are retained for 14 days.
- **Recovery Time Objective (RTO):** Target RTO is typically within minutes for failover to a reader instance, and within 1 hour for restoring from a snapshot.
- **Restore Procedure:**
    1. Navigate to the RDS console.
    2. Select the Aurora PostgreSQL Cluster.
    3. Choose 'Restore to point in time'.
    4. Specify the target date/time for restoration.
    5. Configure the new cluster settings (name, instance class, VPC, etc.).
    6. Initiate the restore process. A new cluster will be created.

### Common Issues
### High CPU Utilization
- **Diagnosis:** Monitor `CPUUtilization` metric in CloudWatch. Identify long-running queries or inefficient application logic.
- **Resolution:** Optimize slow queries (e.g., add indexes, rewrite queries), scale up instance class, or add more reader instances if read load is the cause.

### High Connection Count
- **Diagnosis:** Monitor `DatabaseConnections` metric. Check application connection pooling settings.
- **Resolution:** Implement or tune connection pooling on the application side. Ensure connections are closed properly. Increase `max_connections` parameter if necessary and instance memory allows.

### Replication Lag
- **Diagnosis:** Monitor `AuroraReplicaLag` for reader instances. High lag indicates readers are struggling to keep up with the writer.
- **Resolution:** Ensure reader instances are appropriately sized. Optimize read queries hitting readers. Scale up reader instances or add more readers if read load is high.

## Rollback Procedure
1. **Revert IaC:** Revert the commit in the infrastructure repository that introduced the change.
2. **Apply IaC:** Execute `terraform apply` (or equivalent) to redeploy the previous state.
3. **Database Instance Failover/Restore:** If a new cluster was created, manually delete it and restore from a backup if necessary to revert data state.
4. **Verify Service Health:** Confirm that applications can connect to the database and that operations are normal.
