# Runbook: Aurora PostgreSQL Cluster

## Overview
The Aurora PostgreSQL Cluster provides a highly available and durable relational database service for production workloads. It is configured with one writer instance and two reader instances across two Availability Zones, ensuring high availability and read scalability. RDS Proxy is utilized for efficient connection management, and IAM database authentication enhances security.

## Prerequisites
- AWS CLI configured with appropriate permissions for RDS, KMS, and Secrets Manager.
- IAM user or role with `rds:*`, `kms:*`, `secretsmanager:*`, and `iam:PassRole` permissions.
- Access to the AWS account where the cluster is deployed.

## Architecture
The Aurora PostgreSQL cluster is deployed within the 'App VPC' across two private subnets ('Private Subnet AZ-A', 'Private Subnet AZ-B'). The cluster is encrypted using a KMS key. Database credentials are managed via Secrets Manager, also encrypted with a KMS key. RDS Proxy is configured to front the cluster for optimized connection pooling.

## Operations

### Scaling
1. **Read Replicas**: To scale read capacity, navigate to the RDS console, select the Aurora cluster, and choose 'Add reader'. Specify the instance class and Availability Zone.
2. **Instance Class**: For scaling compute power of the writer or readers, modify the instance class of the instances within the cluster. This typically involves a brief maintenance window.
3. **Auto Scaling**: Aurora does not support automatic scaling of instance classes directly. Scaling strategies for read replicas can be implemented using custom automation that monitors load and adds/removes reader instances.

### Monitoring
Key CloudWatch metrics to monitor include:
- `CPUUtilization` (for writer and readers): High utilization may indicate a need for instance class scaling or query optimization. Alarm threshold: > 80% for 15 minutes.
- `DatabaseConnections` (for writer and readers): High connection counts can impact performance. Alarm threshold: > 85% of `max_connections` for 10 minutes.
- `ReadLatency` and `WriteLatency`: Spikes indicate potential performance bottlenecks. Alarm threshold: Average latency > 50ms for 5 minutes.
- `FreeableMemory` (for writer and readers): Low memory can lead to performance degradation. Alarm threshold: < 20% for 15 minutes.

### Backup & Recovery
Automated backups are enabled for Aurora PostgreSQL. The backup window and retention period (default 7 days) can be configured in the RDS console.
- **Recovery Time Objective (RTO)**: Aim for minutes to a few hours, depending on the size of the database and the restore process.
- **Restore Procedure**: To restore, navigate to the RDS console, select the cluster, and choose 'Restore to point in time'. Specify the desired timestamp and a new cluster identifier. Once restored, update application connection strings to point to the new cluster.

### Common Issues
### High CPU Utilization
**Diagnosis**: Monitor `CPUUtilization` in CloudWatch. Examine slow query logs or use Performance Insights to identify resource-intensive queries.
**Resolution**: Optimize slow queries, add read replicas to offload read traffic, or scale up the instance class of the writer and/or reader instances.

### High Connection Count
**Diagnosis**: Monitor `DatabaseConnections` in CloudWatch. Applications may not be closing connections properly, or connection pooling might be insufficient.
**Resolution**: Implement or optimize connection pooling (e.g., using RDS Proxy). Review application code to ensure connections are closed after use. Increase `max_connections` if appropriate, considering available memory.

### Slow Query Performance
**Diagnosis**: Utilize RDS Performance Insights and slow query logs to identify and analyze problematic queries.
**Resolution**: Tune SQL queries, add or modify database indexes, or consider denormalizing tables if appropriate. Scale up instance class if I/O or CPU is the bottleneck.
