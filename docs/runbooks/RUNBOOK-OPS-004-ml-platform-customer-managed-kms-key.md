# Runbook: ML Platform Customer Managed KMS Key

## Overview
The Customer Managed KMS Key (Key Management Service) is used to encrypt sensitive data at rest, such as data stored in S3 buckets or other services. Using a customer-managed key provides greater control over encryption and access policies.

## Prerequisites
- AWS CLI configured with KMS permissions.
- IAM user or role with `kms:CreateKey`, `kms:DescribeKey`, `kms:Encrypt`, `kms:Decrypt`, `kms:GenerateDataKey` permissions.

## Architecture
A Customer Managed KMS Key is created within the AWS account. This key is then utilized by other AWS services (e.g., S3) to encrypt and decrypt data. Key policies are configured to define which IAM principals and AWS services can use the key.

## Operations

### Scaling
KMS keys themselves do not scale in the traditional sense. The number of API requests to KMS is managed by AWS. If high throughput is required for encryption/decryption operations, consider using AWS KMS's automatic scaling capabilities or designing applications to leverage features like `GenerateDataKey` effectively to minimize direct KMS calls.

### Monitoring
Key CloudWatch metrics for KMS keys:
- `EncryptOperations`, `DecryptOperations`, `GenerateDataKeyOperations`: Monitor the volume of cryptographic operations.
- `KeyUsage`: Track how frequently the key is being used.
- **CloudTrail Logs**: Essential for auditing all actions performed on the KMS key, including key usage, policy changes, and administrative actions.

### Backup & Recovery
KMS keys are durable and automatically replicated across multiple Availability Zones within a region. There is no direct backup or restore procedure for a KMS key itself. If a key is accidentally disabled or scheduled for deletion, it can be re-enabled within a 30-day waiting period. If a key is permanently deleted, it cannot be recovered, and data encrypted with it becomes unreadable.

### Common Issues
### Access Denied when encrypting/decrypting data
- **Diagnosis**: Verify the IAM principal or service attempting the operation has been granted permissions in the KMS key policy and its own IAM policy. Ensure the correct KMS key ARN is specified.
- **Resolution**: Update the KMS key policy and/or the IAM policy to grant the necessary permissions (`kms:Encrypt`, `kms:Decrypt`, `kms:GenerateDataKey`, etc.).

### Data becomes inaccessible after KMS key deletion
- **Diagnosis**: This occurs if a KMS key used for encryption is permanently deleted.
- **Resolution**: Ensure keys are never permanently deleted unless absolutely certain the data is no longer needed and cannot be recovered. If a key is scheduled for deletion, re-enable it before the waiting period expires.

## Rollback Procedure
1. Revert the IaC commit that created or modified the KMS key's configuration or policies.
2. Execute `terraform apply` to remove the KMS key or revert its configuration.
3. If data was encrypted with this key, ensure it is re-encrypted with a different, available KMS key, or that the original key is restored if possible.
