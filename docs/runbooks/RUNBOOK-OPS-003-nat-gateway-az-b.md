# Runbook: NAT Gateway AZ-B

## Overview
The NAT Gateway in Availability Zone B enables instances in private subnets within AZ-B to connect to the internet or other AWS services, while preventing inbound connections initiated from the internet.

## Prerequisites
- AWS CLI configured with appropriate permissions
- Network administrative access
- EIP allocated for the NAT Gateway

## Architecture
Deployed in the public subnet of Availability Zone B. Associated with an Elastic IP address. Route tables for private subnets in AZ-B are configured to route internet-bound traffic (0.0.0.0/0) through this NAT Gateway.

## Operations

### Scaling
1. To scale NAT Gateway capacity, consider provisioning additional NAT Gateways in different Availability Zones or in the same AZ if traffic demands require it.
2. Monitor NAT Gateway metrics (e.g., `BytesOutToDestination`, `PacketsOutToDestination`) to identify potential bottlenecks.

### Monitoring
Key metrics: `BytesOutToDestination`, `PacketsOutToDestination` (monitor for high utilization), `ActiveConnectionCount`. Set alarms for sustained high utilization.

### Backup & Recovery
NAT Gateways are highly available managed services. There is no direct backup or recovery procedure for the NAT Gateway itself. High availability is achieved by deploying NAT Gateways in each Availability Zone and configuring routing accordingly.

### Common Issues
### Outbound Connectivity Failures
- **Diagnosis**: Incorrect route table configuration in private subnets, insufficient Elastic IP addresses, or NAT Gateway is not in the correct subnet.
- **Resolution**: Verify route table entries point to the NAT Gateway. Ensure the NAT Gateway has a valid Elastic IP. Confirm the NAT Gateway resides in a public subnet.

## Rollback Procedure
1. Revert the Infrastructure as Code changes related to the NAT Gateway and associated route tables.
2. Apply the reverted configuration using Terraform.
3. Verify outbound connectivity from private subnets.
