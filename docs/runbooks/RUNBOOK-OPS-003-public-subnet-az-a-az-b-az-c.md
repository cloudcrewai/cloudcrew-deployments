# Runbook: Public Subnet AZ-A, AZ-B, AZ-C

## Overview
These public subnets provide network segments within the VPC that have a direct route to the Internet Gateway. Resources placed in these subnets can be internet-facing, such as bastion hosts or NAT Gateways.

## Prerequisites
- AWS CLI configured with appropriate permissions
- VPC with an attached Internet Gateway
- Route tables associated with these subnets configured for internet access

## Architecture
These subnets (10.0.1.0/24, 10.0.2.0/24, 10.0.3.0/24) reside in separate Availability Zones (a, b, c respectively) within the 'App VPC'. They are configured with route tables that direct internet-bound traffic (0.0.0.0/0) to the Internet Gateway.

## Operations

### Scaling
Subnet IP address range is fixed. To scale capacity beyond the current CIDR block, consider creating additional subnets in the same or different AZs with new CIDR blocks. Scaling of resources within subnets is handled independently (e.g., EC2 Auto Scaling).

### Monitoring
Monitor CloudWatch metrics for Network ACLs associated with these subnets for DENY activity. Analyze VPC Flow Logs to understand traffic originating from or destined to these subnets. Monitor resource utilization (e.g., IP address exhaustion).

### Backup & Recovery
Subnet configurations are part of the overall VPC definition and are managed via Infrastructure as Code. Recovery involves reapplying the IaC configurations.

### Common Issues
### Resources in public subnets cannot reach the internet
- **Diagnosis**: Verify the subnet's route table has a default route (0.0.0.0/0) pointing to the Internet Gateway. Ensure Network ACLs and Security Groups associated with the resources allow outbound internet traffic.
- **Resolution**: Correct the route table configuration. Adjust Network ACLs and Security Groups to permit necessary outbound traffic.

## Rollback Procedure
1. Revert the Infrastructure as Code (IaC) changes related to the public subnets.
2. Apply the reverted IaC using the deployment tool (e.g., `terraform apply`).
3. Verify resources within the public subnets have the expected network connectivity.
