# Runbook: Application Load Balancer

## Overview
The Application Load Balancer (ALB) distributes incoming internet-facing application traffic across multiple targets, such as EC2 instances or containers, in multiple Availability Zones. It provides features like SSL/TLS termination, request routing, and health checks to ensure high availability and fault tolerance for the application.

## Prerequisites
- AWS CLI configured with administrative access or specific ALB management permissions.
- IAM permissions to describe, register, and deregister targets, and to modify listeners and rules.
- Access to CloudWatch for monitoring ALB metrics and logs.

## Architecture
The ALB is deployed in the public subnets of the 'App VPC' across two Availability Zones ('a' and 'b'). It is internet-facing and listens for incoming traffic on standard ports (e.g., 80, 443). It forwards traffic to targets in the private subnets, typically ECS tasks or EC2 instances.

## Operations

### Scaling
1. Navigate to the EC2 console and select 'Load Balancers'.
2. Choose the 'Application Load Balancer' service.
3. Under the 'Listeners' tab, you can add or modify listener rules for traffic routing.
4. Under the 'Target Groups' tab, you can view and manage registered targets. Auto-scaling for targets is configured separately (e.g., within ECS service definitions or Auto Scaling Groups).
5. To manually scale the ALB's capacity, AWS automatically scales it based on traffic load. No manual intervention is required for ALB scaling.

### Monitoring
Key CloudWatch metrics to monitor:
- `HealthyHostCount`: Number of healthy targets. Alarm if below expected count.
- `UnHealthyHostCount`: Number of unhealthy targets. Alarm if above 0.
- `RequestCountPerTarget`: Number of requests processed by each target. Monitor for unusual spikes or drops.
- `HTTPCode_Target_5XX_Count`: Number of 5XX errors returned by targets. Alarm if > 0.
- `HTTPCode_ELB_5XX_Count`: Number of 5XX errors generated by the ALB itself. Alarm if > 0.

### Backup & Recovery
ALBs are a managed service and do not require traditional backups. Their configuration is defined in Infrastructure-as-Code and can be version-controlled. In case of an ALB failure or deletion, the ALB can be recreated by applying the IaC. Target group health checks and auto-scaling configurations ensure resilience.

### Common Issues
### High `HTTPCode_Target_5XX_Count`:
- **Diagnosis**: Indicates errors originating from the backend targets (e.g., application errors, unhealthy instances).
- **Resolution**: Check CloudWatch logs for the backend services, review application error logs, and ensure backend targets are healthy and properly configured.

### High `HTTPCode_ELB_5XX_Count`:
- **Diagnosis**: Indicates errors generated by the ALB itself, often due to capacity issues or misconfigurations.
- **Resolution**: Review ALB resource utilization metrics, check for any recent configuration changes, and ensure the ALB has sufficient capacity (AWS manages this automatically, but extreme traffic spikes can be a factor).

### Application intermittently unavailable:
- **Diagnosis**: Potential issues with health checks, network connectivity between ALB and targets, or insufficient number of healthy targets.
- **Resolution**: Verify health check configurations are accurate and targets are passing them. Ensure proper routing and security group rules allow traffic from ALB to targets. Check target group's `HealthyHostCount`.

## Rollback Procedure
1. Revert the Infrastructure-as-Code commit related to the ALB configuration.
2. Apply the reverted Infrastructure-as-Code using the deployment tool (e.g., `terraform apply`).
3. Verify the ALB's configuration and health checks are restored.
4. Monitor application traffic and target health to confirm successful rollback.
