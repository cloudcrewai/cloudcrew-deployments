# Runbook: NAT Gateway

## Overview
NAT Gateways enable instances in private subnets to connect to the internet or other AWS services, but prevent the internet from initiating connections with those instances.

## Prerequisites
- AWS CLI configured with appropriate permissions
- Elastic IP address available
- NAT Gateway resource configured in IaC

## Architecture
Two NAT Gateways are deployed, one in each Availability Zone ('a' and 'b'), associated with their respective public subnets. They are configured to route outbound traffic from the private subnets.

## Operations

### Scaling
The number of NAT Gateways is determined by the number of Availability Zones requiring outbound internet access. To scale, provision additional NAT Gateways in new Availability Zones if required by the architecture.

### Monitoring
Key metrics include: BytesInFromSource, BytesOutToDestination, ActiveConnectionCount, PacketsInFromSource, PacketsOutToDestination. Monitor for increases in connection counts or data transfer that might indicate high traffic or potential bottlenecks.

### Backup & Recovery
NAT Gateways are managed services. Their state is maintained by AWS. Recovery involves ensuring the associated Elastic IP and public subnet are healthy. If a NAT Gateway fails, AWS typically handles failover or replacement. Configuration is maintained in IaC.

### Common Issues
### High NAT Gateway Usage / Cost
Diagnosis: Monitor `BytesInFromSource` and `BytesOutToDestination` metrics. High sustained usage can lead to significant costs.
Resolution: Analyze traffic patterns. Implement VPC endpoints for services like S3 and DynamoDB to keep traffic within the VPC. Optimize application data transfer. Consider if direct egress is truly necessary for all outbound connections.

## Rollback Procedure
1. Revert the IaC commit related to NAT Gateway configuration.
2. Apply the reverted IaC using `terraform apply`.
3. Verify that instances in private subnets can still access the internet if required.
