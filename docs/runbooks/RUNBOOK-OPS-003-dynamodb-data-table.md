# Runbook: DynamoDB Data Table

## Overview
The DynamoDB Data Table serves as the primary persistent data store for the serverless application. It is a fully managed NoSQL database designed for high-performance, scalable applications.

## Prerequisites
- AWS CLI configured with appropriate permissions.
- IAM permissions to access and manipulate data in the DynamoDB table.
- Knowledge of the table's primary key schema and data structure.

## Architecture
A DynamoDB table configured with `PAY_PER_REQUEST` billing mode, ensuring costs scale with usage. Point-in-time recovery is enabled for data protection. It is encrypted using a customer-managed KMS key (`aws_kms_key.dynamodb`).

## Operations

### Scaling
DynamoDB in `PAY_PER_REQUEST` mode automatically scales read and write capacity based on traffic. There is no manual capacity provisioning or scaling required for this configuration. Ensure the application code handles potential throttling if burst traffic exceeds provisioned capacity (though less common with `PAY_PER_REQUEST`).

### Monitoring
Key CloudWatch metrics to monitor:
- `ConsumedReadCapacityUnits` / `ConsumedWriteCapacityUnits`: Measures the throughput consumed.
- `ProvisionedReadCapacityUnits` / `ProvisionedWriteCapacityUnits`: Relevant if using provisioned capacity, but for `PAY_PER_REQUEST`, these are effectively infinite.
- `ThrottledRequests`: Number of requests throttled due to exceeding capacity.
- `SuccessfulRequestLatency`: Latency of successful requests.

Recommended alarm thresholds:
- `ThrottledRequests` > 0 for 5 minutes (indicates potential throughput limitations or inefficient access patterns).
- `SuccessfulRequestLatency` > 200ms for 5 minutes (indicates potential performance issues).

### Backup & Recovery
Point-in-time recovery (PITR) is enabled, allowing restoration to any point in time within the preceding 35 days. Backups are continuous and managed by DynamoDB.

**Restore Procedure**: 
1. Navigate to the DynamoDB console.
2. Select the `production-serverless-production-data-table`.
3. Choose 'Restore to point in time'.
4. Specify the desired restore date and time.
5. Select a new table name for the restored data.
6. Initiate the restore process. Once complete, update application configurations to point to the new table if necessary.

### Common Issues
### 1. `ProvisionedThroughputExceededException` (or Throttling):
- **Diagnosis**: The table is receiving more read or write requests than it can handle at that moment. While `PAY_PER_REQUEST` auto-scales, sudden bursts can still lead to temporary throttling.
- **Resolution**: Analyze access patterns for hot partitions or inefficient queries. Implement exponential backoff and retry logic in application code. If consistently throttling, consider optimizing queries or, in rare extreme cases, migrating to provisioned capacity if predictable heavy load is confirmed.

## Rollback Procedure
1. Revert the Infrastructure as Code commit that modified the DynamoDB table configuration.
2. Apply the changes using the IaC tool (e.g., `terraform apply`).
3. If data was lost or corrupted, restore the table from a PITR backup to a new table and update application configurations accordingly.
