# Runbook: ML Platform NAT Gateways

## Overview
The NAT Gateways in each Availability Zone provide outbound internet connectivity for resources deployed in the private subnets of the ML Platform VPC. This allows instances to access necessary AWS services and external resources without exposing them directly to the internet.

## Prerequisites
- AWS CLI configured with administrative access for EC2 resources.
- IAM permissions to create, describe, and delete NAT Gateways and Elastic IPs.
- Existing VPC and public subnets.

## Architecture
A NAT Gateway is deployed in each Availability Zone within the public subnets of the ML Platform VPC. Each NAT Gateway is associated with an Elastic IP address. Route tables for the private subnets are configured to direct all outbound internet traffic (0.0.0.0/0) to the respective NAT Gateway in its Availability Zone.

## Operations

### Scaling
1. **Add NAT Gateway**: If additional Availability Zones are added to the VPC and require outbound internet access for private resources, create a new public subnet in the new AZ and deploy a NAT Gateway within it. Update the corresponding private subnet's route table.
2. **Increase NAT Gateway Bandwidth**: NAT Gateways automatically scale their bandwidth. If performance issues arise, review CloudWatch metrics for high `PacketsDropCount` which might indicate a need to investigate traffic patterns or consider architectural changes.

### Monitoring
Key CloudWatch metrics to monitor for each NAT Gateway:
- `ActiveConnectionCount`: Track the number of concurrent connections.
- `BytesInFromSource`, `BytesOutToDestination`: Monitor data transfer volume.
- `PacketsDropCount`: Indicates potential bandwidth limitations or network issues. High values warrant investigation.

### Backup & Recovery
NAT Gateways are managed AWS resources and do not require traditional backups. If a NAT Gateway fails, a new one can be provisioned via IaC. The associated Elastic IP should be re-associated. Ensure route table configurations are correctly reapplied.

### Common Issues
### Resources in private subnets cannot reach the internet
- **Diagnosis**: Verify the NAT Gateway is in a 'Available' state. Check the route table associated with the private subnet; ensure it has a default route (0.0.0.0/0) pointing to the NAT Gateway.
- **Resolution**: Ensure the NAT Gateway is healthy. Correct the route table entries to point to the correct NAT Gateway ID for the respective AZ.

### High `PacketsDropCount` on NAT Gateway
- **Diagnosis**: Indicates the NAT Gateway is unable to keep up with the traffic volume.
- **Resolution**: Analyze traffic patterns using VPC Flow Logs to identify the source of high traffic. Consider if the current architecture can be optimized or if resources in private subnets require more bandwidth.

## Rollback Procedure
1. Revert the IaC commit that modified or removed the NAT Gateway resources.
2. Execute `terraform apply` to remove the NAT Gateway or restore its previous configuration.
3. Verify that resources in private subnets can now access the internet as expected.
