# Runbook: ML Platform Private Subnets

## Overview
The private subnets are integral components of the ML Platform VPC, designed to host sensitive SageMaker resources such as training jobs and inference endpoints. They provide network isolation by default, preventing direct inbound access from the internet.

## Prerequisites
- AWS CLI configured with IAM permissions to manage VPC resources, specifically subnets and route tables.
- An existing VPC with appropriately sized CIDR blocks for private subnets.

## Architecture
Two private subnets are provisioned, one in each Availability Zone ('a' and 'b'), with CIDR blocks 10.0.11.0/24 and 10.0.12.0/24 respectively. These subnets are configured with route tables that direct outbound traffic through the NAT Gateways located in the public subnets, allowing necessary communication with AWS services and external resources while maintaining inbound security.

## Operations

### Scaling
1. **Add Private Subnets**: To increase capacity or distribute resources across more Availability Zones, additional private subnets can be created. This involves defining new `aws_subnet` resources in Terraform for the desired AZs and assigning them appropriate CIDR blocks.
2. **CIDR Block Expansion**: If a private subnet's CIDR block (e.g., /24) becomes insufficient for the number of resources, it can be expanded (e.g., to /23), provided adjacent IP space is available within the VPC's overall CIDR block. This requires careful planning and IaC updates.

### Monitoring
Key metrics to monitor for resources within private subnets:
- **Network In/Out**: Track data transfer volume for instances and services.
- **VPC Flow Logs**: Essential for auditing traffic between resources and to/from the internet via NAT Gateway.
- **Resource-Specific Metrics**: Monitor CPU, memory, and disk I/O for compute instances or SageMaker endpoints residing in these subnets.

### Backup & Recovery
Subnets themselves are network configurations and do not store data. Recovery from a subnet configuration issue involves reverting the IaC definition and reapplying it. If resources within a private subnet become unavailable due to network misconfiguration, the recovery procedure will depend on the specific resource's backup and restore capabilities.

### Common Issues
### Resources cannot communicate with each other within private subnets
- **Diagnosis**: Review Network Access Control Lists (NACLs) and Security Groups associated with the resources and subnets. Check if inter-subnet communication is permitted.
- **Resolution**: Adjust NACLs and Security Groups to allow necessary traffic between resources. Ensure route tables are correctly configured for intra-VPC communication.

### Resources cannot access external AWS services (e.g., S3, SageMaker API)
- **Diagnosis**: Verify the route table associated with the private subnet correctly points to the NAT Gateway for `0.0.0.0/0` traffic. Check if VPC endpoints for required services are configured and accessible.
- **Resolution**: Correct route table configuration. Ensure VPC endpoints are properly set up and security groups allow access to them.

## Rollback Procedure
1. Revert the IaC commit that modified the private subnet configurations (CIDR, route tables, NACLs).
2. Execute `terraform apply` to restore the previous subnet definitions and routing.
3. Verify that resources within the private subnets can communicate internally and externally as expected.
